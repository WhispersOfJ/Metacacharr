# Full-Stack Audit Findings

Architectural issues noted during the audit but not fixed (out of scope for a small/obvious fix). See `AUDIT_PROGRESS.md` for directory-by-directory status.

## Pre-existing (found during plan recon, before directory 1)

- ~~**No global exception handler** in `control-panel/main.py`.~~ **Fixed post-audit (2026-08-19):** `_discover_routers()`'s per-router import is now wrapped in try/except — a broken router import logs via the shared logger and is skipped, instead of crash-looping every other router along with it. This is not a hypothetical: it's exactly what happened live during this audit's Directory 6 verification (a stale image with a dangling `os.environ["RADARR_ANIME_API_KEY"]` read crash-looped the entire container). `_startup()`'s DB setup remains unguarded on purpose — a DB failure should stop boot, not degrade silently — but now logs a "startup complete" line so a crash there is visible in the log file, not just `docker logs`. Verified live: rebuilt, container boots clean and healthy; 3 new tests in `tests/control_panel/test_main_router_discovery.py` confirm a simulated broken router import is isolated and logged rather than fatal.
- **STACK.md service-count header is stale.** `## Full service inventory (all 17, by subsystem)` (STACK.md:114) undercounts against the same doc's own later text ("`up -d` starts all 26 daemon services", STACK.md:259). Not a functional bug, just a doc nit — worth a one-line header fix whenever STACK.md is next touched.

## Directory 2: control-panel/core/

- **`DEDUP_SUFFIX_RE` (`control-panel/core/arr_client.py:282`) is ambiguous between a dedup suffix and a bare year.** The regex `\s\(\d+\)(\.[A-Za-z0-9]+)?$` matches both `"Movie Name (2).mkv"` (a real Radarr/Sonarr dedup suffix) and `"Movie Name (2020).mkv"` (a normal year-suffixed filename with no dedup collision at all) — `dedup_suffix_hit("Movie Name (2020).mkv")` returns `True`. Whatever consumes `dedup_suffix_hit()` should be checked for whether a false positive on a plain year-suffixed title causes an incorrect action (e.g. treating a normal file as a duplicate). Not fixed here since narrowing the regex (e.g. requiring the digit count to be short, or checking against a known dedup-count range) is a behavior change, not an obvious fix.
- **`control-panel/main.py`'s module docstring is stale.** It says the module "Runs ALONGSIDE the existing app.py during the phased migration" — but `app.py` was fully retired in the 2026-08-05 backend rewrite and deleted from disk entirely in this audit's Directory-1 commit. Doc nit, not touched here to stay in scope for the logging task.

## Directory 3: control-panel/services/ + main.py + models/

- **`AuditLog` (`control-panel/models/audit_log.py`) is write-only.** `services/auth/router.py` writes `login`, `login_failed`, and `logout` rows, but nothing anywhere in `services/` or `static/` ever reads the table back — no `/api/audit-log` route, no admin view in the frontend. The data is captured but never surfaced. Not fixed here (adding a read endpoint + UI is new functionality, not a small/obvious fix), but worth a deliberate decision: either build the reader or stop writing rows nobody looks at.
- **`main.py:40-41`'s `_own_network_gateway` has a silent `except Exception: pass`.** Best-effort gateway lookup used for `ALLOWED_HOSTS`; a failure here just means the app falls back to a narrower host allowlist, not a hard failure. Left unlogged since it's outside the `services/` scope of this directory pass and the fallback is intentional — flagged for the next pass over `main.py` itself if one happens.
- **`services/host/router.py`'s automation-exception comments are borderline.** `log_levels_reset` (line 387) and `notify_test` (line 574) rely only on the module-level header explaining the `current_user_or_service` exception, not a route-local comment like every other router in `services/` uses. Not changed here since the module header does cover it, just weaker than the codebase's usual per-route convention — worth tightening if `host/router.py` is touched again.

## Directory 4: control-panel/static/

- **`palette.js` and `auth.js` cannot be imported without a live DOM.** Both do `document.getElementById(...)` at module top level (not inside a function), so `node --test` (or any Node-based tooling) can't even load these files — confirmed via `node -e "import('./palette.js')"` throwing `ReferenceError: document is not defined`. This means every pure-logic helper inside `palette.js` (`fuzzyMatch`, `matchRank`, `pathEscape`, `queryEscape`, `parseApiResult`, `prepareCommand`, `summarizeConsoleItem`, `indentDict`, `renderConsoleResult` — none of which touch the DOM themselves) is structurally untestable in isolation. Not fixed here: the repo has zero DOM-shim tooling (no jsdom, no package.json at all — tests run via bare `node --test` against ES modules), and adding one is a tooling decision, not a small/obvious audit fix. If these functions are ever revisited, moving the DOM lookups into the functions that use them (deferring `document.getElementById` to call time, same pattern already used everywhere else in `static/js/`) would fix this for free.
- Every other `static/js/` file (14 of 16 non-test files) imports cleanly under plain Node and was checked; all exported DOM-wiring functions were read but not unit-tested since they require a live DOM to exercise meaningfully — flagged as a structural gap above rather than worked around.

## Directory 5: scripts/

- No architectural issues found. `scripts/` is thin, well-reasoned operational tooling — every script already fails loudly (`sys.exit`/`SystemExit` with a specific message) rather than swallowing errors, and the two `.sh` files (`notify-discord.sh`, `check-container-health.sh`) already have deliberate, commented reasoning for their one genuinely-silent exit paths (missing/placeholder webhook URL — intentional no-op, explained inline).
- `provision-cleanuparr-instances.py`'s `main()` return code (`return 1 if failed else 0`) only reflects `provision_instances` failures, not a `provision_seeker` fetch failure (which now prints a FAILED line but doesn't flip the exit code to 1). Not changed here — deciding what counts as a fatal vs. a printed-warning failure across this script is a behavior call, not a small fix, and the failure is at least now visible in stderr instead of crashing unhandled.

## Directory 6: systemd/ + Dockerfile + entrypoint.sh

- **Two real dangling references to a compose profile that was never defined.** `systemd/media-stack.service` (`ExecStart=`/`ExecStop=`/Description) and `entrypoint.sh`'s first-run help text both referenced `docker compose --profile extras ...` and named Bazarr/Byparr/Kometa (all removed or, for Byparr, never present). `docker-compose.yml` has exactly one profile anywhere (`"scheduled"`, on `plexanisync`) — no `extras` profile exists or ever did in the current file. Confirmed via `docker compose --profile extras config --services` that this was harmless in practice (compose profiles are additive, so requesting a nonexistent one just adds nothing — all 18 default-profile services still started), but it's a landmine: if a real profile is ever added under a different name, this stale flag would silently exclude it with no error. Fixed both: dropped `--profile extras` from `media-stack.service` and `entrypoint.sh`, updated the stale service-name comment.
- **`.claude/skills/health-monitor/monitor.py`'s `SCHEDULED_JOBS` dict only monitors 1 of 9 real `.timer` units** (`plexanisync.timer` — confirmed a real, correct reference). The other 8 scheduled jobs (arr-backup, bearmount-prune-history, docker-prune, health-check, letterboxd-sync, plex-report, poster-sync-movies, poster-sync-shows) have no staleness/failure detection through this mechanism — a silently-broken cron-equivalent job wouldn't be caught the way a stale `plexanisync` run now is. Not fixed here: this file lives outside the plan's scope (`.claude/skills/`, not `scripts/`/`systemd/`/`Dockerfile`/`entrypoint.sh`), and expanding `SCHEDULED_JOBS` for 8 more jobs with correctly-tuned max-age thresholds is new functionality, not a small fix.
- Every other unit file, the root `Dockerfile`, and `entrypoint.sh` were clean: all `ExecStart=`/`ExecStartPre=` paths resolve to real executable files, every `OnFailure=notify-failure@%n.service` reference resolves to the real templated unit, every `.timer` has a matching `.service` and vice versa, the 4 timer-less services are legitimately so (2 boot-time/`WantedBy=default.target`, 2 long-running daemons with `Type=simple`), and all root `Dockerfile` `COPY` sources exist on disk.
- **`control-panel/Dockerfile:19` (a second Dockerfile, distinct from the root one already checked above) had a build-breaking dangling `COPY app.py ...` reference.** `control-panel/app.py` was deleted from disk in this session's consolidation work, but the Dockerfile still tried to copy it into the image, plus a now-stale comment explaining app.py's "kept temporarily as a rollback reference" status. Missed on the first pass through this directory because the automated `find` for Dockerfiles only surfaced the root one by habit; caught during the mandatory live verification step (log-file spot-check) when `docker compose build control-panel` failed outright with `"/app.py": not found`. Fixed: dropped `app.py` from the `COPY` line (kept `settings_store.py`, confirmed still present and imported) and removed the stale comment. Rebuilt and confirmed the container now boots clean.
- **Live verification also caught a second, unrelated real bug**, exposed only by forcing a container recreate against current `docker-compose.yml`: the *previously running* `control-panel` container had been up for 7 hours on a stale image (built 2026-08-15, predating this session's anime-instance retirement), so `docker compose up -d` alone (no `--build`) recreated it against the current compose file's env vars but the OLD image's code — and the old image's `core/arr_client.py` unconditionally read `os.environ["RADARR_ANIME_API_KEY"]` at import time, a var Directory 1 had already correctly removed from `docker-compose.yml`. Container crash-looped (`KeyError: 'RADARR_ANIME_API_KEY'`) until rebuilt with `--build`. Not a bug in current source (grepped: zero `ANIME` references left in `core/arr_client.py`) — purely an artifact of a stale image not being rebuilt after the anime-retirement commit landed. No code fix needed; documented here because it's the exact "restart vs. rebuild" landmine this repo's `feedback_control_panel_hard_reload_verification` memory already warns about, now confirmed to bite the backend image too, not just frontend static assets.
